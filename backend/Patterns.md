# Паттерны проекта

Документ фиксирует архитектурные решения, конвенции кода и принципы, принятые в проекте. Служит ориентиром при добавлении новых сервисов и рефакторинге существующих.

## Файловая архитектура (Стандарт сервиса)
```
service_name/
├── api/                  # Слой API: FastAPI роутеры
│   ├── router.py         # Эндпоинты (только валидация и вызов сервиса)
│   └── README.md
├── services/             # Слой Services: Чистая бизнес-логика
│   ├── domain_logic.py   # Оркестрация процессов
│   └── README.md
├── repositories/         # Слой Repositories: Доступ к данным
│   ├── sql_repo.py       # Работа с PostgreSQL (ORM/SQL)
│   ├── nosql_repo.py     # Работа с MongoDB/Redis
│   └── README.md
├── core/                 # Слой Core: Инфраструктура и UoW
│   ├── uow.py            # Unit of Work
│   ├── config.py         # Настройки сервиса (Pydantic)
│   ├── exceptions.py     # Кастомные исключения
│   └── README.md
├── workers/              # (Опционально) Background Workers (RabbitMQ)
├── clients/              # (Опционально) Внешние клиенты (SMTP, API)
├── main.py               # Точка входа, lifespan, bootstrap
└── README.md
```

### Структура `shared/` (Общая библиотека)
Пакет `shared` не следует 4-х слойной архитектуре, так как является библиотекой инфраструктурных компонентов. Он разбит на функциональные модули:
- `database_core/` / `mongodb_core/`: Базовые классы для работы с БД.
- `rabbitmq/`: Обертки для Message Bus.
- `models/` / `schemas/`: Общие сущности и DTO.
- `bootstrap/`: Логика инициализации контейнера зависимостей.
- `utils/`: Вспомогательные функции (логирование, исключения).

## 1. Архитектура

### 1.1 Микросервисы
Каждый бизнес-домен изолирован в отдельном сервисе со своим `Dockerfile`, `.env`, `requirements.txt`. Сервисы не импортируют код друг друга напрямую — общий код вынесен в пакет `shared/`.

### 1.2 API Gateway (Go)
Клиент взаимодействует **только** с `gateway_service` (порт 8000). Gateway:
- Проксирует запросы через `forward_request`.
- Выполняет аутентификацию (middleware) и PIN-gate.
- Инжектирует заголовки `X-Internal-Key` и `X-User-ID` перед пересылкой.
- Микросервисы доступны только внутри Docker-сети `backend`.

### 1.3 Resource-Based REST API
- Ресурсы — существительные во множественном числе (`/accounts`, `/transactions`).
- Действия определяются HTTP-методами (`POST` — создание, `GET` — получение, `DELETE` — удаление).
- **Идемпотентность**: Финансовые операции поддерживают заголовок `X-Idempotency-Key` для предотвращения дублей.
- Pydantic v2 для строгой валидации и типизации.

## 2. 4-Слойная структура (Layered Architecture)

Все бизнес-сервисы следуют строгому разделению на слои для обеспечения инверсии зависимостей (DIP) и тестируемости.

### 2.1 Слои (Layers)
1.  **API Layer (`api/`)**: Роутеры. Принимают HTTP-запросы, валидируют входные данные через схемы, вызывают Service. Не содержит бизнес-логики.
2.  **Domain Layer (`services/`)**: Чистая бизнес-логика. Работает с абстракциями. Не знает о деталях БД или API. Координирует работу репозиториев.
3.  **Data Layer (`repositories/`)**: Инкапсулирует работу с хранилищами.
    - **SQL (SQLAlchemy)**: Транзакционная работа с PostgreSQL.
    - **NoSQL (MongoDB/Redis)**: Хранение логов, кэша, сессий.
4.  **Core Layer (`core/`)**: Инфраструктурный клей. Содержит Unit of Work (управление атомарностью), конфигурацию и доменные исключения.

### 2.2 Дополнительные слои
- **Workers Layer (`workers/`)**: Консьюмеры RabbitMQ для асинхронной обработки задач (уведомления, логирование).
- **Clients Layer (`clients/`)**: Интеграции с внешними API (SMTP, платежные шлюзы, курсы валют).
- **Domain Events**: События, происходящие в домене (напр., `AccountFrozen`), которые должны иметь побочные эффекты в других частях системы.
- **Entity**: Модели БД (SQLAlchemy).
- **Value Objects**: Pydantic-схемы для передачи данных.

## 3. Паттерн Unit of Work (UoW)

UoW является единственным владельцем сессии базы данных в рамках одного запроса.

### 3.1 Основные принципы
- Сервис получает `uow` через `Depends`.
- Все изменения в БД производятся через репозитории, доступные в `uow`.
- `uow.commit()` фиксирует транзакцию и автоматически публикует накопленные события.
- В случае ошибки в бизнес-логике `uow` гарантирует откат (rollback) в `__aexit__`.

### 3.2 Domain Events в UoW
```python
# Пример использования в Service
async def some_action(uow: AbstractUnitOfWork, ...):
    async with uow:
        # Бизнес-логика...
        uow.add_event(NotificationEvent(type="some_type", ...))
        await uow.commit() # Здесь события улетают в Message Bus
```

## 4. Обработка ошибок

Единый стандарт через глобальный middleware `setup_exception_handlers`.

1.  Все бизнес-ошибки наследуются от `BaseBusinessError`.
2.  Класс ошибки определяет `status_code` и `title`.
3.  Микросервис выбрасывает исключение -> Middleware мапит его в красивый JSON-ответ.

**Стандарт ответа:**
```json
{
  "error": "AccountNotFound",
  "message": "Счёт не найден",
  "status_code": 404
}
```

## 5. Работа с данными (CQRS и Хранилища)

### 5.1 Command Query Responsibility Segregation (CQRS)
Мы разделяем потоки изменения и чтения данных для оптимизации производительности.
- **Write**: Через `SqlAlchemyUnitOfWork` и `BaseRepository`. Гарантирует консистентность.
- **Read**: Через `BaseQueryRepository` и сырой SQL (`text()`). Избегает оверхеда ORM при сложных Join-ах.

### 5.2 Технологический стек данных
- **PostgreSQL (Core)**: Основное хранилище (Transactional).
- **PostgreSQL (History)**: Append-only лог действий пользователей (`user_actions`).
- **Redis (Sessions)**: Сессии пользователей (TTL 30 мин).
- **Redis (Onboarding)**: Черновики регистрации (JSON, TTL 15 мин).
- **Clickhouse**: Аналитика бизнес-метрик (High-performance OLAP).
- **MongoDB**: Журналы уведомлений и журналы безопасности (NoSQL, TTL индексы).

## 6. Межсервисное взаимодействие (EDA)

Система построена на принципах **Event-Driven Architecture**.

### 6.1 Message Bus
Все события из UoW попадают в `MessageBus`, который распределяет их по соответствующим Exchange в RabbitMQ:
- `notifications`: Для отправки Email (Consumer: `notification_service`).
- `logs`: Для аудита и аналитики (Consumer: `log_service`).

### 6.2 Внутренняя безопасность (`X-Internal-Key`)
Все межсервисные HTTP-вызовы защищены заголовком `X-Internal-Key`. Проверка осуществляется через `Depends(verify_internal_key)` на уровне всего приложения FastAPI.

## 7. Конвенции разработки

### 7.1 Код
- **Типизация**: Обязательное использование Type Hints везде.

 ## 8. Управление конфигурацией и Bootstrapping
 
 Проект использует систему **Bootstrap** для централизованного управления зависимостями и настройками. Это позволяет легко переключать окружения и мокать ресурсы в тестах.
 
 ### 8.1 Источник истины (APP_ENV)
 Единственный внешний переключатель режима работы — переменная `APP_ENV`.
 - `local`: Разработка (использует `.env`).
 - `test`: Тесты (включает логику переопределения `DATABASE_URL` на тестовую БД и индексацию Redis).
 - `dev`/`prod`: Продакшн (игнорирует локальные `.env`, использует переменные контейнера).
 
 ### 8.2 Pydantic Settings
 Настройки описываются классами в `shared/config/`. Благодаря `pydantic-settings`, мы получаем:
 - Валидацию типов при старте.
 - Автоматическое чтение из `.env`.
 - **Self-adjustment**: Например, `DatabaseSettings` сам меняет свой URL на тестовый, если видит `APP_ENV=test`.
 
 ### 8.3 BootstrapContainer
 Глобальный контейнер (`shared/bootstrap/container.py`), который инициализируется один раз при старте сервиса.
 
 **Основные возможности:**
 - **Ленивая инициализация**: База данных (`engine`), сессии (`session_factory`) и брокер сообщений создаются только при первом обращении.
 - **Жизненный цикл**: Контейнер предоставляет метод `dispose()`, который корректно закрывает все пулы соединений при выключении приложения.
 - **Унифицированный доступ**: Весь инфраструктурный объект доступен через `get_container()`.

 ## 9. Автоматизированный аудит и качество кода
 
 Для поддержания чистоты кодовой базы используется автоматизированная система аудита, запускаемая в изолированном Docker-контейнере.
 
 ### 9.1 Инструменты аудита
 - **Ruff**: Линтер и форматировщик. Проверяет стиль кода (PEP 8), импорты и современные стандарты Python.
 - **Vulture**: Поиск «мертвого» кода (неиспользуемые функции, классы, переменные).
 - **Deptry**: Аудит зависимостей (выявляет неиспользуемые или отсутствующие пакеты в `requirements.txt`).
 
 ### 9.2 Конфигурация
 Конфигурация аудита вынесена из корня проекта в инфраструктурный слой для поддержания чистоты репозитория:
 - Путь к настройкам: `infra/audit/pyproject.toml`
 - Скрипт запуска: `infra/audit/audit.sh`
 
 ### 9.3 Запуск
 Аудит запускается единой командой из папки `backend/`:
 ```bash
 docker compose run --rm audit
 ```
 
 Система автоматически монтирует конфиги и выполняет полную проверку всех микросервисов. Любые изменения в стандартах кодирования должны вноситься в центральный файл `pyproject.toml`.
