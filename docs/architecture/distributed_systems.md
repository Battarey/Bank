# Распределенные системы и Идемпотентность

В микросервисной банковской системе возникают специфические проблемы распределенных вычислений: сетевые сбои, повторные запросы (retries) и конкурентный доступ к балансам.

## 1. Идемпотентность API

Для защиты от дублирования транзакций (например, при двойном клике пользователя или повторном запросе от клиента при таймауте) используется заголовок **`X-Idempotency-Key`**.

-   **Механизм**: При получении запроса с ключом идемпотентности, система проверяет, был ли запрос с таким ключом успешно обработан.
-   **Результат**: Если запрос уже обрабатывался, система возвращает сохраненный результат выполнения, не производя повторных списаний.

## 2. Конкурентность и Блокировки (Pessimistic Locking)

При переводе средств между счетами система должна гарантировать, что баланс не изменится в процессе выполнения транзакции другим процессом.

-   **Стратегия**: Используется `SELECT FOR UPDATE` на уровне базы данных.
-   **Изоляция**: Это блокирует строку счета до завершения текущей транзакции (коммита или отката), гарантируя консистентность баланса.

## 3. Предотвращение Deadlocks

Взаимные блокировки могут возникнуть, если два процесса пытаются перевести деньги друг другу одновременно:
- Процесс А: блокирует Счет 1, ждет Счет 2.
- Процесс Б: блокирует Счет 2, ждет Счет 1.

**Решение**: Алгоритм сортировки ресурсов.
Перед выполнением блокировок, система всегда сортирует идентификаторы счетов (например, по возрастанию UUID). Оба процесса будут пытаться заблокировать сначала меньший ID, затем больший, что исключает возможность циклического ожидания и возникновения Deadlock.
