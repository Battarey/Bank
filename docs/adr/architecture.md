# ADR 0001: Выбор микросервисной архитектуры и технологического стека

## 1. Контекст

При проектировании современной банковской платформы необходимо обеспечить:
-   **Отказоустойчивость**: Сбой в сервисе уведомлений не должен мешать проведению платежей.
-   **Масштабируемость**: Различные части системы имеют разную нагрузку (Gateway и Auth нагружены сильнее, чем Security).
-   **Гибкость данных**: Нужно сочетать строгие транзакции (ACID) с быстрой аналитикой (OLAP).

## 2. Решение

Принято решение использовать **микросервисную архитектуру** со следующим разделением ответственности и технологий:

### 2.1 API Gateway на Go
-   **Почему**: Go обладает превосходной производительностью при работе с сетевыми соединениями и минимальным потреблением памяти. Это идеальный выбор для шлюза, который выполняет только проксирование и первичную проверку сессий.

### 2.2 Бизнес-сервисы на Python (FastAPI)
-   **Почему**: Python позволяет быстро разрабатывать сложную бизнес-логику (AML, расчеты). FastAPI обеспечивает высокую скорость работы благодаря асинхронности (async/await) и встроенную валидацию через Pydantic.

### 2.3 Разделение хранилищ (Polyglot Persistence)
-   Использование **PostgreSQL** для финансовых данных (Core).
-   Использование **ClickHouse** для аналитики (высокая скорость агрегации).
-   Использование **Redis** для горячих данных (сессии, кэш).

### 2.4 Асинхронное взаимодействие через RabbitMQ
-   Использование **Event-Driven Architecture (EDA)** для всех побочных эффектов. Это позволяет основному потоку транзакции не ждать завершения отправки письма или записи в аналитику.

## 3. Последствия

### Положительные:
-   Изоляция компонентов: сервисы можно обновлять и перезапускать независимо.
-   Возможность независимого масштабирования узких мест.
-   Высокая скорость ответа API Gateway.

### Отрицательные (риски):
-   Усложнение инфраструктуры (необходимо управлять 10+ контейнерами).
-   Необходимость контроля распределенной консистентности (решено через паттерн Unit of Work и идемпотентность).
