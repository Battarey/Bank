# Идентификация и Контроль доступа

Безопасность системы строится на принципе многоуровневой проверки полномочий пользователя: от сетевого шлюза до конкретного микросервиса.

## 1. Сессионные токены (X-Session-Token)

Основным механизмом авторизации является заголовок `X-Session-Token`, который выдается `auth_service` после успешного входа (POST /sessions).

-   **Хранение**: Токены хранятся в **Redis Sessions**.
-   **Валидация**: Проверка токена происходит на уровне **Go Gateway** при каждом запросе. Это позволяет мгновенно блокировать доступ без нагрузки на бизнес-сервисы.
-   **Sliding Expiration**: Время жизни сессии (TTL) продлевается автоматически при каждом активном действии пользователя.

## 2. PIN-gate (Второй фактор)

Система реализует механизм **PIN-gate** для защиты финансовых операций и доступа к чувствительным данным.

-   **Принцип**: После входа по логину/паролю пользователь получает сессию, но с флагом `has_pin=false`.
-   **Ограничение**: Пока флаг `has_pin` не станет `true`, Gateway блокирует доступ ко всем эндпоинтам, кроме смены/установки PIN и выхода из системы.
-   **Активация**: Пользователь должен отправить PIN-код (отдельный запрос), после чего Gateway обновляет статус сессии в Redis.

## 3. Защита межсервисных вызовов (Internal-Key)

Внутренние микросервисы (Python) доверяют запросам от шлюза (Go Gateway) и друг от друга на основе секретного ключа.

-   **Заголовок**: `X-Internal-Key`.
-   **Проверка**: На уровне каждого FastAPI приложения работает Middleware, который сравнивает значение заголовка с эталоном из переменных окружения (`INTERNAL_API_KEY`).
-   **Цель**: Предотвращение подделки запросов (Request Spoofing) даже в случае компрометации внутренней сети.

## 4. Изоляция PII (Personal Identifiable Information)

Данные клиентов (паспортные данные, адреса) шифруются перед сохранением в базу данных. Ключи шифрования хранятся отдельно, что минимизирует риск утечки данных при прямом доступе к БД.
